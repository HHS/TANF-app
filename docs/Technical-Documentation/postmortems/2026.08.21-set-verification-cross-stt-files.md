## Root cause

### Login.gov SET key verification

Full details can be found in the Security Advisory: [GHSA-w5f9-6g83-v6mc](https://github.com/raft-tech/TANF-app/security/advisories/GHSA-w5f9-6g83-v6mc)

Original implementation of Login.gov Security Event Tokens had "verify_signature": False in the JSON Web Token (JWT) decode. This means a self-signed JWT could be used to create SETs, instead of only a Login.gov-signed JWT.

PR [#5303](https://github.com/raft-tech/TANF-app/pull/5303), [Line](https://github.com/raft-tech/TANF-app/blob/119285520a28f33ab923ce340ab2df05c7a79213/tdrs-backend/tdpservice/security/views.py#L112) - Merged 10-25-2025, released in [v4.5.0](https://github.com/raft-tech/TANF-app/releases/tag/v4.5.0)

This was likely an artifact of testing - we cannot properly sign Json Web Tokens with the Login.gov private key when testing locally or in test environments, so `verify_signature` must be `False`. This flag was likely committed and merged by mistake and was not caught in PR review.

- Is there a way to verify things like this in the pipeline? on commit hooks, secrets check, etc. - Husky?

### Cross-STT data file submissions:

Full details can be found in the Security Advisory: [GHSA-52h9-r64r-4jq3](https://github.com/raft-tech/TANF-app/security/advisories/GHSA-52h9-r64r-4jq3)

Original implementation of get_requested_stt permissions used `ChainMap(view.kwargs, request.query_params, request.data)`, meaning `query_params` was validated before the `POST` body for data file submissions. This could be used to change which STT the file was submitted for, bypassing the permission guard by using the STT allowed for the user in the `query_params`.

PR [#1286](https://github.com/raft-tech/TANF-app/pull/1286), [Line](https://github.com/raft-tech/TANF-app/blob/420efa35411cf94c798d28e4796c516fec031584/tdrs-backend/tdpservice/users/permissions.py#L96) - Merged 10-19-2021, released in [v1.0.0](https://github.com/raft-tech/TANF-app/releases/tag/v1.0.0)

This could have technically been exploited in any version of TDP by modifying requested in DevTools to include the `?stt=X` query parameter and changing the `POST` body STT to the target location. However, it was made more easily exploitable when API authentication was introduced via PR [#5814](https://github.com/raft-tech/TANF-app/pull/5814), merged 05-27-2026, released in [v4.20.0](https://github.com/raft-tech/TANF-app/releases/tag/v4.20.0)

This was seemingly an implementation mistake. `ChainMap` maps all the given parameters, regardless of request type, and gives preference to the `query_params` (since they come first). This allows the `query_params` value to override what is provided in the `POST` body for the authorization step, but the `POST` body is used to create the object in the serialization step.

## Impact

We have not yet found any indication of either of these issues being exploited, but system logs are not comprehensive for either.

### Login.gov SET key verification

When decoding a JSON Web Token (JWT), `verify_signature` allows the system to determine whether the JWT was signed by a specific private key by using a public key. In our case, Login.gov signs the JWT with their private key and we use their public key to validate the JWT actually came from Login.gov and was not modified.

Without `verify_signature`, we do not determine if the key was signed by Login.gov. An attacker could submit any self-signed JWT with any payload they want and our system would have treated it as legitimate. The `/v1/security/event-token` endpoint requires no authentication by design, since Login.gov cannot authenticate to our system before submitting a request. The JWT signing is meant as a substitute for authorization. This means any attacker could create a Security Event Token for any account in the system, provided they know the target account's Login.gov UUID (information required in the payload).

The most impactful result possible was that an attacker could disable the target user's account. Other possible actions are enabling the target account and changing the target account's email address. Other SET types only log a message and do not change account details.

We checked the created Security Event Tokens in the Django Admin Console for any suspicious operations. We see the following counts for each event

- `ACCOUNT_DISABLED`: 0 events
- `ACCOUNT_PURGED`: 4 events
- `EMAIL_CHANGED`: 5 events
  - Some of these events had no associated user, as late as 8/25/2026 - investigate https://github.com/raft-tech/TANF-app/pull/5862
- `EMAIL_RECYCLED`: 3 events

Because the logs cannot tell us who created each event token, there's no way for us to tell if the events are created legitimately or maliciously. The best option is to monitor user reports for locked-out accounts and investigate/respond individually. No such reports were mentioned.

What would help catch this in the future?

- Regular security audits, security audit tools
- Security pentesting - supposed to be done every year, hasn't been done in a couple years
- Verify signature setting in the pipeline via git hooks, secrets check, Husky, etc.

### Cross-STT data file submissions

Because the STT provided in `query_params` in a POST request to the `/v1/data-files` endpoint were taking precidence over the STT provided in the request body, a user could submit a file to a location for which they are not authorized.

This required the user to be authorized for the location used in `query_params`, even if they were not authorized for the location provided in the `POST` body, limiting the potential impact.
We could audit all submitted data files to find where a file's `submitted_by` user belonged to a location different than the file was submitted for. Alex did this, only 1 user submitted for a jurisdiction that was not their own (Arizona, which is authorized to submit for Tribes). The `submitted_by` user could technically be swapped as well, but would require knowledge of another user's UUID (unlikely).

Another option is to monitor user reports for files submitted for an STT that did not belong to that STT. We did not receive any such reports.

What would help catch this in the future?

- If data for a particular STT looks incorrect (unless submitted something plausible) - feedback reports done regularly
- Exceptions table - STTs that a user is allowed to submit for
- Developers/Code review - validate the information that is used to create the object, don't validate query params over post data, etc

## Resolution steps

Both fixes were addressed in a single hotfix PR, with one added patch to invert the `settings.DEBUG` value as noted in the timeline. The hotfix was released 08-21-2026 at 4:20pm ET and validated in production at 5:15pm ET.

### Login.gov SET key verification

Enabled `verify_signature` in staging and production environments by using `not settings.DEBUG`. This enforces JWT key verification when the setting is `False`, but still enables local testing.

### Cross-STT data file submissions

Updated the `get_requested_stt` function to check `request.method` and apply `query_parameters` to the `ChainMap` only on `GET` requests, and use only the `POST` body on `POST` requests. This allows the function to still be used for both request types, but limits authorization to only the fields used by the subsequent queries/serializers.
