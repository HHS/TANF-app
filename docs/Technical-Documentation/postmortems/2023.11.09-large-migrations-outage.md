# Postmortem, production deployment issues related to migrations

- Author: Jan Timpe
- Postmortem Attendees: Connor Smith, Alexandra Pennington, Andrew Jameson, Jan Timpe, Mo Sohani, Eric Lipe, George Hudson, Tom Tignor
- Incident Date: September 7, 2023 - November 9, 2023
- Postmortem Date: 12/08/2023

## Timeline

- 09/07/2023 - sprint 80 deployment failed
  - https://github.com/HHS/TANF-app/pull/476
  - deleted previously deployed migration, search_indexes 0016 (\*)
  - comment `makemigrations`/`migrate` in deployed environments to force manual migrations

- unable to deploy to prod during this time (develop pipelines blocked for various reasons)

- 09/20/2023 - initial event - sprint 82 deployment failed
  - https://github.com/raft-tech/TANF-app/releases/tag/v3.1.5-Sprint-82
  - uncomments `makemigrations`/`migrate`
  - recreates broken search_indexes 0016
  - disk space error
  - large migration identified (search indexes 0017)

- staging issues prevent deployment to prod
  - mo discovers cf revisions

- 11/01/2023 - Unblocking prod working session, attempt to reproduce issue in raft environment
  - https://mattermost.goraft.tech/goraft/pl/553xig6qetbydenskzap7bh8uh
  - Upload a large amount of data (700k-1m rows each of t1, t2, t3, t4, t5)
  - Run migrations from local environment against deployed db (by following https://hackmd.io/8TUNc7nhSOWJv4vkpHqveQ)
  - Inspecting `temp_files` space and database size before/during/after migration
  - db size would increase up to 8x, reduces back to beginning level after migration completes
    - by making migrations smaller, maybe we can limit the db size increase during the migration
  - `temp_files` would increase ~4gb after migration completion
  - were not able to reproduce the issue at the time, migrations would run on the raft environment even though the number of database records was substantially larger than in prod
  - attributed this to a difference in some db settings, would bring to team next office hours to devise path forward

- 11/03/2023 - Attempt to work through the issue in office hours
  - Identified possible resolution paths in https://hackmd.io/8TUNc7nhSOWJv4vkpHqveQ
    - split large migrations into multiple smaller ones
    - increasing postgres `tmp_file_limit`
    - increase db instance storage in cloud.gov
    - wipe temp table space by creating a new db instance from a backup

- 11/06/2023 - Attempt to reduce `tmp_file_limit` and db instance storage in raft environment (to reproduce the issue)
  - lowering db instance storage to 20gb allowed us to reproduce the issue after running migrations multiple times, as the temp space eventually exceeded the instance size

- 11/08/2023 - Attempt to restore prod meeting
  - increase the db instance size in production and re-run migrations
  - notes - https://hackmd.io/8TUNc7nhSOWJv4vkpHqveQ
  - noticed a new error related to converting a blank string to an integer
  - many possible instances in the offending migration, would go on to attempt to manually determine which field was blank with no success
  - using "check for blank strings in CharFields" function in "Debugging commands", was able to isolate the fields in T3 causing the error
  - turned out that every character field in T3 has some records where the field was given a value of `''` (blank string) rather than `None` as expected
  - would go on to reproduce this issue in the raft environment by uploading a datafile containing affected rows and running the migration, could get the migration to run successfully by changing all blank strings to `None`
  - inspecting affected rows revealed that T3 rows were submitted with a single case file, but no space-filling for the second case
  - due to a python substring idiosyncracy, these were falling through our `value_is_empty` check during parsing, and being created as blank strings.
  - creation of first empty strings fix pr, would eventually be re-created into https://github.com/raft-tech/TANF-app/pull/2748
  - designated next steps were to
    - create a new production database from a backup
    - drop all data in `search_indexes` tables
    - redeploy sprint 82 release

- 11/09/2023 - Attempt to restore prod meeting
  - to avoid creating a new db, would go on to
    - create a backup of the production database
    - truncate all of the `search_indexes` tables
    - redeploy spring 82 release
  - production is restored to sprint 82 and deployments can move forward
  - t3 records with no space-fill will cause an exception that stops parsing with no records created for the file, fixed by https://github.com/raft-tech/TANF-app/pull/2748

## Root cause

multiple incidents combined into one

- migration 0016 deleted/recreated caused initial deployment issues, complexity related to fixing deployment
- substringing bug
  - exacerbated by not having correct field types in models to begin with (migrations would not have failed, deployments not blocked)

## Resolution steps

- create a backup of the production database
- truncate all of the `search_indexes` tables - were not worried about losing production data
- redeploy spring 82 release
- fix empty strings bug

## Moving forward

- Unplanned work, had a lot of developers contribute
  - unique situation, small team means that everyone is needed to weigh in on their area of expertise
    - can we empower the team so that less people need to be pulled off current work to address issues?
    - wiki pages, operations playbooks - outline common problems and responses
    - https://github.com/raft-tech/TANF-app/blob/develop/docs/Technical-Documentation/Failed-Deployment-Troubleshooting.md - create a section for database issues, cf revisions command
    - create a github repo of changes done directly to prod, can serve as a guide for similar future issues
    - document SOONER
    - save terminal output from production debugging sessions
- Migration management (create guidelines to be enforced in code reviews) - https://levelup.gitconnected.com/django-database-migrations-best-practices-and-common-pitfalls-9a0086bd4948#:~:text=Always%20keep%20your%20migration%20files,reliable%20history%20of%20schema%20changes.
  - do _NOT_ edit migrations that have already been ~~deployed to production~~ merged to develop, write a new migration to modify the model from that point
  - rename auto-generated migration names, hard to investigate without more descriptive names
  - use auto-generated migrations wisely, one per-model change, regenerate if making successive changes in one pr
- Deploying to other environments
  - have occasionally deployed in-progress code to raft/qasp/sandbox and changed migrations after the fact, causes conflicts in that environment
- untested cases
  - large datasets
  - unexpected edge cases (no space-fill)
  - (!) having a way to duplicate the production database (with PII scrubbed) would allow us to run more tests against 'real-world' data
